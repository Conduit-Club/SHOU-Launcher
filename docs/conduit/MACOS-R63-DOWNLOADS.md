# R63：内置下载并发与重复校验（2026-11-16）

本轮按用户要求提高新实例下载速度，接续尚未合并的 `features/windows-parity` 缺陷修复；本地基点为 `c3fa1b4`，与 origin 同步、较 origin/dev 领先 257 提交且没有分叉。R63 验收时尚未提交或推送；之后按用户明确授权，将已验证修复交接到同一分支与 PR #15，供 Windows 端继续开发。候选仍保留验收时的旧基点 dirty 标记，不改写来源。未合并、发布、覆盖个人安装或启动 Minecraft。

## 修改

- 内置总并发默认直接设为 **256**，配置和设置页上限同为 256。参照旧 WPF `Modules/Network/Facade/ModNet.cs` 的 256 总连接上限和单文件 8 连接；旧 WPF 默认 64、新端旧默认 8。本轮按用户“拉满”的要求采用上限作为默认值。
- 库、资源、整合包文件和 Java 下载不再被旧的 8/4 文件生产队列截断；内置传输和 aria2 仍共享实际连接预算。排队由释放名额唤醒，移除 25 ms 轮询间隙。缓存核对和旧文件复制不占网络名额。
- 已保存的旧默认 8、且没有并发配置修订标记时，一次性提升到 256；新版本写入标记，之后用户明确改回 8 也能保留。其他已设置值保留，可自行调低。旧配置中曾手动选择 8 与旧默认无法区分，同样会进行这次迁移。
- 有已知大小和哈希的大文件，从 8 MiB 起使用最多 **8 路 HTTP Range**。以每路约 1 MiB 的有界窗口预取，顺序写入及计算哈希，不把完整文件放进内存；取消后保留连续前缀，后续可续传。来源不支持分段时回退普通传输。
- 普通和分段下载均边写入边计算元数据提供的 SHA-1/SHA-256，移除下载完成后重新整文件读盘的校验阶段；已有缓存同时校验两种哈希时也只读一遍。旧目录复用在复制时计算哈希，省去复制后的再读盘。
- 元数据没有哈希的 Maven 库，不再强制额外请求 `.sha1`。这类库显式允许复用已有非空文件；有声明大小时仍比对大小。无哈希目录/清单默认继续获取新内容，不将目录响应当作可复用的库文件。
- 传输超时按无数据活动计算；用户主动限速的排队等待不计为网络停顿，避免高并发低限速时反复超时重下。取消、错误源回退、原文件的原子替换保持有效。

## 验证

Core 全量 **971 通过 / 11 条件跳过 / 0 失败**；最后的下载、限速、旧文件复用及 RPC 回退专项 **52/52**。完整 Headless **389 通过 / 3 条件跳过**，包含默认 256 和自定义值即时保存。Windows x64 交叉编译通过，所有最终构建 0 警告/错误。

真实本机 HTTP 服务、256 个 16 KiB 文件、每次响应延迟 60 ms；对同一最终下载器设置不同并发：

| 并发设置 | 实测峰值连接 | 耗时 |
| --- | --- | --- |
| 8 | 8 | 2116 ms |
| 64 | 64 | 316 ms |
| 256 | 256 | 149 ms |

这验证并发实际生效，不是旧发行版与新包的完整对比，也不保证外网带宽具有相同比例的提升。回归还覆盖双哈希、真实 8 路 HTTP Range、不支持 Range 的两种回退、取消后按前缀续传、多大文件共享名额、损坏内容不覆盖原文件，以及无需 `.sha1` 的库安装和缓存复用。
